# Development Leads — release and data handling

This workspace uses the same Deal Desk URL and login. It is independent of New Opportunities, underwriters, exports and the Contacts/Deals backing tables. There is no realtime subscription, shared board, or publish action for sourcing snapshots. Existing team administrators have no app role override for another owner's Development Leads. The project operator/service credentials are privileged as usual; never use an administrator query as evidence of a user's authenticated view.

## Release order

1. Confirm the existing site targets the connected database project. Take catalog-only preflight evidence for the three new table names, new API names, and untouched legacy access policies. Verify the exact candidate against a disposable PostgreSQL database and browser fixtures only. **Never seed production.**
2. Apply `supabase/migrations/003_private_development_leads.sql` in one transaction. It adds three tables and four scoped RPCs only; the member/administrator membership check uses the existing team table read-only. `p_actor` must match the existing token identity and never routes rows to a caller-selected recipient. The RPC queries scope every read and write to `auth.uid()`. Direct data-table privileges are not available to anonymous/authenticated application roles, and RLS is enabled. Recheck metadata from the live project: function ACLs, RLS, and absence of any change to old policies. No production prospect queries. If the write acknowledgment is uncertain, reconcile from catalog before retrying.
3. Push only source/test changes on the exact existing main parent. Verify the canonical site loads the new JS/CSS, no bundled research. In an **existing** intended-owner session, open Development Leads and check the displayed login and empty/expected state, without creating any test rows. Never mint/mask/imitate an owner session in production. Installation, signed-in verification and private data load are separate gates.

## Authorized real import (separate step)

- Validate the reviewed file locally against [schema v1](development-leads-format.md); record source date, distinct site/parcel counts and normalized file fingerprint without logging addresses. Keep the approved file in private storage (0700 directory, 0600 file). Do not send it to a third-party importer, attach it to a Git commit, or use the production public shell for data QA.
- Use only the existing **verified intended-owner** Deal Desk session. In Development Leads → Manage research, confirm the account label, Preview the local JSON, compare the count/date and only then Import private snapshot. The UI re-reads the result in the same user session; after reload confirm count/date and only the reviewed sites, with no record showing up in New Opportunities. No writes even to the new tables until this operation is separately authorized. An admin credential is not a substitute for the active user's session. Do not import on behalf of an arbitrary email/account.
- Identical normalized data is idempotent. An older identical snapshot is recognized but remains inactive until explicitly restored. Import/restore compares the active version; each lead save compares its record revision and active version. Rollback can restore a previous snapshot or pause the active list from history without deleting research or resetting owner edits. A changed parcel set needs a fresh stable site ID.
- Built-in backup: retained immutable research versions and Download research JSON for the active source. The download does not include notes or other owner activity; retain the normal database backups for full recovery. No private research is added to the existing global export path. Reverting this release's Git commit affects the UI only; leave the new tables and saved work in place. Do not drop production tables as a rollback.
- Draft Contact/Deal is an explicit handoff to an unsaved private form. No bulk transfers, updates to existing records, or automatic lookups in a lead-origin deal. Only an explicit existing form Save creates a record. Any further intentional publication in those separate workflows is a different action.
